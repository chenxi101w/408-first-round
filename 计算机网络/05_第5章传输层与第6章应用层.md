## 知识点详解

### 一、传输层解决什么问题（5.1，书 224 页）

三层的"谁给谁"是三个层次，别混：

| 层次 | 通信单位 | 地址 | 是否逐跳变化 |
|---|---|---|---|
| 链路层 | 相邻节点（点到点） | MAC 地址 | 每跳都变（A→R1 是 A 的 MAC，R1→R2 换成 R1 的 MAC） |
| 网络层 | 主机到主机 | IP 地址 | 自始至终不变 |
| 传输层 | **进程到进程（端到端）** | 端口号 | — |

老师用寄快递类比：IP 地址是收件人和寄件人，中间怎么转运不用你管；MAC 地址只是每一段运输的交接凭证。

一台电脑同时开 QQ 和微信给另一台电脑发消息，网络层看到的只是"一堆数据"，分不出谁发的；到接收方的传输层才按端口把数据**分开**投递给对应软件。这就是**复用/分用**存在的理由。

差错检测的分工（选择题原话）：

- IP 首部校验和**只检查首部**；
- 传输层校验和**首部和数据一起检查**；
- TCP 发现出错 → 重传（可靠）；UDP 发现出错 → 直接丢弃，或报告上层（不可靠）。

### 二、复用与分用（5.1.2）

- **复用**：发送方多个应用进程的数据混在一起交给 IP，靠**源端口**区分"是谁发的"。
- **分用**：接收方按**目的端口**把数据交给对应进程。

> 课后 15 题的坑就在这：问"复用依据什么"→ 源端口；问"分用依据什么"→ 目的端口。老师明确点过这道题。

### 三、端口号与套接字（5.1.2）

端口号 **16 位**，编号范围 **0~65535**，可表示**65536 个**。注意区分"编号"和"个数"：编号到 65535，个数是 65536 = 2^16。顺带背 2^15 = 32768、2^16 = 65536，组成原理也常用。

| 类别 | 范围 | 说明 |
|---|---|---|
| 熟知端口 | 0~1023 | 固定分配给常用服务：HTTP 80、FTP 21（控制）/20（数据）、DNS 53、SMTP 25、POP3 110 |
| 登记端口 | 1024~49151 | 给需要备案的应用，如 MySQL 3306 |
| 短暂端口 | 49152~65535 | 客户端临时申请，每次通信可能不同（这次 4 万多、下次 5 万多） |

端口号本身考试不深究，**只需记住 0~1023 是服务器用的熟知端口**。
（具体端口数值如 80/21/20/53/25/110 为教材补充，课程只要求记住"0~1023 属于服务器"这一层。）

**套接字（socket）= IP 地址 + 端口号**，唯一标识某台主机上的某个进程。真题没直接考过，开发网站会用到。

### 四、UDP 的特点与首部（5.2，书 226~227 页）

UDP 只做"复用/分用 + 差错检测"两件事，其余全不管：

- 无连接（不发握手，直接封包就发）；
- 不可靠（不确认、不重传、不排序、不去重）；
- 首部开销小：**8 字节**；
- 无流量控制、无拥塞控制 → 发送速率不受网络状况约束，**实时性好、延迟低**。

适用场景：视频会议、IP 电话、流媒体、DNS 查询——"丢几句听不清影响不大，但延迟半小时就没法开会"。

**首部 8 字节，四个字段各 16 位**：

| 字段 | 长度 | 含义与取值 |
|---|---|---|
| 源端口 | 16 位 | 发送进程端口；不需要对方回复时可全 0 |
| 目的端口 | 16 位 | 接收进程端口，分用的依据，必须有 |
| 长度 | 16 位 | **首部 + 数据**的总长度，单位字节，**最小 8**（只有首部无数据），最大 65535 |
| 校验和 | 16 位 | 对"伪首部 + 首部 + 数据"做反码求和后取反；IPv4 中填 0 表示不校验 |

**易混**：UDP 的"长度"含数据；IP 首部的"首部长度"只含首部且以 4 字节为单位。这两个字段同名不同义。

三个首部长度必须背下来（老师原话"有一年考过"）：

| 协议 | 首部长度 |
|---|---|
| IP | 20 B（最小，可更大） |
| TCP | 20 B（最小，最长 60 B） |
| UDP | **8 B** |

### 五、UDP 校验和的计算（5.2.2）

计算时要在 UDP 报文前**临时加一个 12 字节伪首部**（源 IP 4 B + 目的 IP 4 B + 全 0 1 B + 协议号 17 1 B + UDP 长度 2 B）。伪首部**只参与计算，不随报文发送**。

算法（二进制反码求和）：

1. 把伪首部 + UDP 首部 + 数据按 **16 位**分组，数据部分不是偶数个字节时**末尾补一个全 0 字节**；
2. 各组按二进制相加；**最高位产生的进位要回卷加到最低位**（end-around carry）；
3. 把最终结果**按位取反**，写入校验和字段。

接收方验证：把所有 16 位字（**含校验和字段**）再反码求和，结果应为**全 1**（0xFFFF）。

道理：发送方算出的校验和是"其余部分之和的反码"，两者相加必为全 1。

**例（课后 16，24 年真题，UDP 校验和唯一一次选择题）**：题干给出前几步相加的中间结果，要求再与下一个 16 位字相加并求校验和。

- 按上述规则相加（含进位回卷）得中间和 `0000 1111 1011 1100`（0x0FBC）；
- 取反 → `1111 0000 0100 0011`（0xF043），选 **C**；
- 验算：0x0FBC + 0xF043 = 0xFFFF，正确。

> 干扰项必然有一个"忘记取反"的答案。老师提醒："很多人一算到一半看到选项就选了"——算完必须再取反一次。
> （字幕中逐位相加的数字口播含糊，此处按"中间和与校验和互补"验算，答案 C 与课堂一致。）

### 六、TCP 的特点与首部（5.3.1，书 233~235 页）

TCP 的"可靠"四个字要能背全：**无差错、不丢失、不重复、有序**。

- **全双工**：A、B 各有发送缓存和接收缓存，A→B 与 B→A 是两条独立通路，序号也各编各的；
- **面向字节流**：TCP 把应用层交下来的数据看成连续字节流，按**字节**编号，不保留报文边界（这是后面所有序号题的根）。

**首部格式**：前 20 字节固定，后面可有选项，最长 60 字节（20 + 40）。

| 字段 | 位数 | 含义 |
|---|---|---|
| 源端口 | 16 | 发送进程 |
| 目的端口 | 16 | 接收进程，实现分用 |
| **序号 seq** | 32 | **本报文段所携带数据的第一个字节的编号** |
| **确认号 ack** | 32 | **期望收到对方下一个报文段第一个字节的序号**；仅当 ACK=1 时有效 |
| **数据偏移** | 4 | 即首部长度，单位 **4 字节**；最大 15 → 首部最长 **60 B** |
| 保留 | 6 | 置 0 |
| **控制位** | 6 | URG、ACK、PSH、RST、SYN、FIN，各 1 位 |
| **窗口** | 16 | **接收窗口 rwnd**，单位字节，告诉对方"我还能收多少" |
| **校验和** | 16 | 首部 + 数据（加伪首部），算法同 UDP |
| 紧急指针 | 16 | URG=1 时指出紧急数据末尾位置 |
| 选项 | 0~40 B | 如 MSS、窗口扩大、时间戳 |

控制位逐个说清：

| 位 | 含义 | 典型用途 |
|---|---|---|
| SYN | 同步序号，请求建立连接 | 第 1、2 次握手为 1 |
| ACK | 确认号字段有效 | 除第 1 次握手外基本都为 1 |
| FIN | 发送方数据已发完，请求释放连接 | 第 1、3 次挥手为 1 |
| RST | 复位连接（教材补充） | 端口不存在、严重差错、异常中止时置 1，立即断开 |
| URG | 紧急指针有效 | 紧急数据插队 |
| PSH | 推送，要求尽快交付上层 | 交互式应用 |

两个高频陷阱：

1. **数据偏移的单位是 4 字节**（IP 的片偏移单位是 8 字节，别串）；4 位最大 15，所以首部最长 15×4 = 60 B。
2. **首部里的"窗口"是接收窗口**，但它的作用是**限制对方的发送窗口**——本质是自己收得下多少，效果是压对方发多快。这就是流量控制的实现方式。

### 七、序号与确认号（全章地基）

**定义**：

- 序号 = 本报文段数据**第一个字节**的编号；
- 确认号 = **期望收到**的对方下一个报文段第一个字节的编号。确认号 = N 表示"**N−1 及之前的字节全部收到**"（累积确认）。

**"序号是字节序号，不是报文段序号"**——这是最容易错的一句话，展开说：

- TCP 面向字节流，把整条连接上发送的字节从初始序号开始**一个字节编一个号**；
- 一个报文段只是字节流中的一段，它的序号是这段里**第一个字节**的编号；
- 所以长度 200 B 的报文段，占掉 **200 个编号**，下一段序号是"本段序号 + 200"，而不是 +1；
- 对比链路层的滑动窗口：那里是**一帧编一个号**（帧号），TCP 是**一字节编一个号**（字节号）。同样的"滑动窗口"思想，编号粒度完全不同。

**三个换算式（必须肌肉记忆）**：

```text
末字节编号   = 起始序号 + 长度 − 1
下一段起始   = 起始序号 + 长度
上一段起始   = 本段起始 − 上一段长度
```

**老师举的数字**：从 100 开始、长度 200 的段 → 占 100~299，序号 = 100；收齐后确认号 = 300（不是 299，也不是 200）。

**序号消耗规则**（计算题必用）：

| 报文 | 是否携带数据 | 是否消耗一个序号 |
|---|---|---|
| 第 1 次握手 SYN | 不携带 | **消耗 1 个**（seq=x） |
| 第 2 次握手 SYN+ACK | 不携带 | **消耗 1 个**（seq=y） |
| 第 3 次握手 ACK | **可以携带数据** | 携带数据时 seq=x+1 就是数据首字节 |
| FIN | 一般不携带 | **消耗 1 个** |

### 八、三次握手（5.3.2，书 235~236 页）

```text
        主机 A                                            主机 B
   CLOSED                                                 LISTEN
          |                                                 |
          |  ①  SYN=1, seq=x                                |
          |------------------------------------------------>|  SYN-SENT → SYN-RCVD
          |                                                 |
          |  ②  SYN=1, ACK=1, seq=y, ack=x+1                |
          |<------------------------------------------------|
          |                                                 |
          |  ③  ACK=1, seq=x+1, ack=y+1                     |
          |------------------------------------------------>|  ESTABLISHED
   ESTABLISHED                                              |
```

逐步拆：

1. **第 1 次**：A 发 `SYN=1, seq=x`，不携带数据，但**消耗序号 x**。含义："我想建连接，我的初始序号是 x。"
2. **第 2 次**：B 回 `SYN=1, ACK=1, seq=y, ack=x+1`。两个动作合一：ACK=1 表示"x 我收到了，下一个要 x+1"；SYN=1 表示"我也要建连接，我的初始序号是 y"。B 的 y 与 A 的 x **完全独立**。
3. **第 3 次**：A 回 `ACK=1, seq=x+1, ack=y+1`。此时 A 已能携带数据，seq=x+1 就是第一个数据字节的编号；同时告诉 B"y 收到了，下一个要 y+1"。

**x+1 的两种理解**（老师要求两种都会）：

- 从自己看：上次发到 x，序号顺延，下一个就是 x+1；
- 从对方看：B 的确认号是 x+1，说明 B 要 x+1，那就发 x+1。
- 两者必须一致，这就是握手能自洽的原因。

**为什么是三次而不是两次**：

- 两次只能做到"B 确认了自己的发送能力和 A 的接收能力"，A 无法确认"B 收到了我的 SYN"，B 也无法确认"A 收到了我的初始序号 y"。第三次 ACK 才让**双方的发送/接收能力、双方的初始序号全部得到确认**。课堂上老师的说法是"先测一下 B 能不能收到，能收到再正式发数据"。
- （教材补充）更关键的一条：防止**已失效的连接请求**。若 A 早先的某个 SYN 在网络中滞留，迟到了 B，两次握手时 B 一回 SYN+ACK 就认为连接建立，会空等一个根本不存在的数据源，白白占用缓存和端口；三次握手下 A 不会对这个旧 SYN 回第三次 ACK，B 就不会建立连接。

**两个细节**：

- 前两次握手**不能携带数据**，第三次**可以**（所以第 54 题里数据从 x+1 开始算）；
- 半连接：B 收到 SYN 后、收到第三次 ACK 前处于 SYN-RCVD，此时连接尚未建立。

### 九、四次挥手与状态（5.3.2，书 236~237 页）

```text
        主机 A                                              主机 B
   ESTABLISHED                                            ESTABLISHED
          |                                                   |
          |  ①  FIN=1, seq=u                                  |
          |-------------------------------------------------->|  FIN-WAIT-1 → CLOSE-WAIT
          |  ②  ACK=1, seq=v, ack=u+1                         |
          |<--------------------------------------------------|
          |        （A→B 方向已关；B→A 仍可继续发数据，序号由 v 推进到 w）
          |  ③  FIN=1, ACK=1, seq=w, ack=u+1                  |
          |<--------------------------------------------------|  LAST-ACK
          |  ④  ACK=1, seq=u+1, ack=w+1                       |
          |-------------------------------------------------->|  CLOSED
   TIME-WAIT（等 2MSL）→ CLOSED
```

逐条对应：

1. A 发 `FIN=1, seq=u`（消耗序号 u），表示"A 没有数据要发了"。
2. B 回 `ACK=1, seq=v, ack=u+1`：确认收到 u。注意此时 **B→A 方向没关**，B 还能继续发数据。
3. B 数据发完后发 `FIN=1, ACK=1, seq=w, ack=u+1`。**seq 从 v 变成 w**，就是因为中间又发了若干数据；**ack 仍是 u+1**，因为 A 在这期间没再发新数据。
4. A 回 `ACK=1, seq=u+1, ack=w+1`，然后进入 **TIME-WAIT**，等 2MSL 才 CLOSED。

**为什么挥手要四次**：TCP 是**全双工**，两个方向各自独立关闭。A 的 FIN 只关掉 A→B 这一个方向（半关闭），B 可能还有数据没发完，不能把 ACK 和 FIN 一起发；只能先回 ACK 表示"知道你要关了"，等自己数据发完再单独发 FIN。两个方向各需一次 FIN + 一次 ACK，共四次。
（若 B 恰好也没数据要发，第 2、3 次可合并成一次，变成"三次挥手"——这是允许的，做小题时要会。）

**状态迁移**：

| 状态 | 含义 | 谁进入 |
|---|---|---|
| CLOSED | 关闭 | 初始/最终 |
| LISTEN | 监听连接请求 | 服务器 |
| SYN-SENT | 已发 SYN，等对方 SYN+ACK | 客户 |
| SYN-RCVD | 收到 SYN 并回了 SYN+ACK | 服务器 |
| ESTABLISHED | 连接已建立，可传数据 | 双方 |
| FIN-WAIT-1 | 已发 FIN，等 ACK | 主动关闭方 |
| FIN-WAIT-2 | 收到 ACK，等对方 FIN | 主动关闭方 |
| CLOSE-WAIT | 收到对方 FIN 并回 ACK | 被动关闭方 |
| LAST-ACK | 已发 FIN，等最后 ACK | 被动关闭方 |
| TIME-WAIT | 等 2MSL 后关闭 | 主动关闭方 |

**TIME-WAIT 等 2MSL 的原因**（老师："这个很关键，考试出现过好几次"）：

1. **保证最后一个 ACK 能到达 B**。若第 4 次 ACK 丢失，B 会超时重发 FIN；A 还在 TIME-WAIT 就能再回一次 ACK。如果 A 发完 ACK 立刻 CLOSED，B 重发的 FIN 永远无人应答，B 就永远关不掉。等 2MSL 正好覆盖"B 重发 FIN + 我回 ACK"一个来回。
2. （教材补充）让本连接产生的**所有旧报文段在网络中消亡**（MSL 是报文最大生存时间），防止它们干扰之后用相同四元组建立的新连接。

**关闭总耗时**（考过多次）：

- 主动关闭方（客户机）：**1 RTT + 2MSL**；
- 被动关闭方（服务器）：**1.5 RTT**。

理由：A 从发 FIN 到收 B 的 FIN 恰好一个往返（1 RTT），之后还要等 2MSL；B 从收到 FIN（0.5 RTT）到收到最后的 ACK（1.5 RTT）。

### 十、可靠传输：超时重传与快重传（5.3.3，书 237 页）

TCP 靠四件套保证可靠：**校验、序号、确认、重传**。重传分两种：

| 方式 | 触发条件 | 时机 |
|---|---|---|
| 超时重传 | 计时器到期仍未收到确认 | 慢，要等满一个 RTO |
| 快重传（冗余 ACK） | 收到 **3 个重复/冗余 ACK** | 立即重传，不等计时器 |

**冗余 ACK 的判定**：发送方连续收到对**同一个序号**的确认（例如一直收到 ack=100），说明 100 号开始的那段丢了，后面的段都到了但接收方无法按序交付，只能反复催 100。收到第 3 个冗余 ACK 就立即重传，这种技术叫**快速重传**。

**例（课后 51）**：T0 收到 ack=100，随后发出起始 100、长度 100 的段（100~199），该段丢失。之后发 200、300、400，接收方每次都回 ack=100。

- 第 1 个 ack=100 是正常确认（对 100 号之前的确认）；
- 之后 3 个 ack=100 是**冗余 ACK**；
- 若支持快重传 → 在 **T3** 重传；若只按超时重传 → 在 **T4** 重传。
- 结论：快重传比超时重传早一个时间段，这就是"快"的含义。

### 十一、流量控制与滑动窗口（5.3.4，书 238~239 页）

目的：**不让发送方发得太快，使接收方来得及接收**。

机制：

1. 接收方把自己接收缓存的剩余空间写进 TCP 首部的**窗口字段**（rwnd），随 ACK 一起发回；
2. 发送方维持一个**发送窗口**，窗口内是"已发送未确认 + 可发送未发送"的字节；
3. 约束：**未收到确认的数据量 ≤ rwnd**；
4. 每收到一个确认，窗口前沿向前滑动——这就是滑动窗口。

**发送窗口的最终取值**：

```text
发送窗口 = min(接收窗口 rwnd, 拥塞窗口 cwnd)
```

- rwnd 反映**接收方**的接收能力（流量控制）；
- cwnd 反映**网络**的承载能力（拥塞控制）；
- 两者取小，谁更紧就听谁的。老师反复强调"题目同时给两个窗口，一定取最小值"。

**零窗口与坚持定时器**（教材补充，课程未展开，但选择题会沾）：

- 接收缓存满 → 通告 rwnd=0，发送方停发；
- 若"窗口更新"报文丢失，双方会互相死等（发送方等窗口更新，接收方等数据）→ **死锁**；
- 解决：发送方设**坚持定时器（persistence timer）**，超时后发一个**1 字节的窗口探测报文**，接收方必须回当前窗口值，从而打破死锁。

**窗口扣减的算法**（课后 57 的核心）：已发送但未被确认的数据仍然**占用窗口**。所以新窗口 = 通告窗口 − 在途未确认字节数。

### 十二、拥塞控制（5.3.5，书 240~241 页，必考大题）

**先分清两个"控制"**：

| | 拥塞控制 | 流量控制 |
|---|---|---|
| 范围 | **全局**，整个网络堵了，所有主机一起减速 | **点对点**，某个接收方收不过来，单独让它慢 |
| 依据 | 拥塞窗口 cwnd（网络能力） | 接收窗口 rwnd（接收方缓存） |
| 谁控制谁 | 发送方根据网络状况自我约束 | 接收端抑制发送端 |

**三个概念**：

- **cwnd（拥塞窗口）**：发送方维护，单位是 **MSS**（最大报文段长度）。cwnd=24 表示"这一轮最多能发 24 个 MSS"。
- **ssthresh（慢开始门限/阈值）**：慢开始与拥塞避免的分界。
- **MSS**：题目常给 MSS=1 KB，用于把"窗口"换算成字节数。

**四个阶段**：

| 阶段 | 规则 | 曲线形状 |
|---|---|---|
| 慢开始 | cwnd 从 1 开始，**每收到一个 ACK 加 1**（一个 RTT 内收到 cwnd 个 ACK → 翻倍） | 指数上升 |
| 拥塞避免 | cwnd ≥ ssthresh 后，**每经过一个 RTT 加 1** | 线性上升（斜率 1/RTT） |
| 快重传 | 收到 **3 个冗余 ACK** 立即重传丢失段 | — |
| 快恢复 | ssthresh = cwnd/2，**cwnd = 新 ssthresh**，直接进入拥塞避免 | 跌一半后线性上升 |

**ssthresh 的调整规则（最容易错）**：

| 事件 | ssthresh | cwnd | 之后 |
|---|---|---|---|
| **超时**（判断为严重拥塞） | **拥塞时 cwnd 的一半** | **1** | 慢开始 |
| **3 个冗余 ACK**（轻微拥塞） | **拥塞时 cwnd 的一半** | **= 新 ssthresh** | 拥塞避免（快恢复） |

两条铁律：

1. 减半的对象是**发生拥塞那一刻的 cwnd**，**不是原来的 ssthresh**。例：ssthresh=16，cwnd 涨到 24 时超时 → 新 ssthresh = 24/2 = **12**，不是 16/2=8。
2. **超时才回到 1**；三个冗余 ACK 走快恢复，cwnd 直接落在新阈值上，**不回 1**。

**拥塞窗口随 RTT 的数值表**（以老师课堂上画的图为例：初始 cwnd=1，ssthresh=16，cwnd 涨到 24 时发生拥塞）：

| 传输轮次（RTT） | 阶段 | 本轮 cwnd（MSS） | 说明 |
|---|---|---|---|
| 第 1 轮 | 慢开始 | 1 | 初始 cwnd=1，ssthresh=16，只发 1 个 |
| 第 2 轮 | 慢开始 | 2 | 收 1 个 ACK 加 1，累计翻倍 |
| 第 3 轮 | 慢开始 | 4 | |
| 第 4 轮 | 慢开始 | 8 | |
| 第 5 轮 | 慢开始 → 拥塞避免 | 16 | 到达 ssthresh，此后每轮只 +1 |
| 第 6 轮 | 拥塞避免 | 17 | |
| 第 7 轮 | 拥塞避免 | 18 | |
| 第 8 轮 | 拥塞避免 | 19 | |
| 第 9 轮 | 拥塞避免 | 20 | |
| 第 10 轮 | 拥塞避免 | 21 | |
| 第 11 轮 | 拥塞避免 | 22 | |
| 第 12 轮 | 拥塞避免 | 23 | |
| 第 13 轮 | 拥塞避免 | 24 | **发生超时** |
| 第 14 轮 | 慢开始 | 1 | ssthresh = 24/2 = 12，cwnd 回 1 |
| 第 15 轮 | 慢开始 | 2 | |
| 第 16 轮 | 慢开始 | 4 | |
| 第 17 轮 | 慢开始 | 8 | |
| 第 18 轮 | 慢开始 → 拥塞避免 | **12** | 翻倍会到 16 > 12，只能取 12 |
| 第 19 轮 | 拥塞避免 | 13 | |
| 第 20 轮 | 拥塞避免 | 14 | |
| 第 21 轮 | 拥塞避免 | 15 | |
| 第 22 轮 | 拥塞避免 | 16 | |

若同一点走**快恢复**（收到 3 个冗余 ACK）：ssthresh = 12，cwnd 直接从 24 落到 **12**（不是 1），然后 13、14、15、16……

**曲线描述（答题/画图按这个说）**：

- 第 1~5 轮：1→2→4→8→16，**陡峭的指数上升**（慢开始）；
- 第 5~13 轮：16→24，**斜率固定为 1 的直线**（拥塞避免）；
- 超时点：**垂直跌到 1**，形成一个"锯齿"的谷底；随后在 ssthresh=12 处被"削平"，8 之后不再翻倍而是升到 12，再线性爬升（12→13→14→15→16）；
- 快恢复点：**只跌到 12**（原值的一半），曲线下凹幅度小、回升快，所以叫"快恢复"。

**"每收一个 ACK 加 1"与"每 RTT 翻倍"的统一**（老师特意标"注意"，大题小问常错）：

- 翻倍不是瞬间完成的。cwnd=1 时发 1 个，收到 1 个 ACK → cwnd=2；cwnd=2 时发 2 个，收到第 1 个 → 3，收到第 2 个 → 4；cwnd=4 时收到 4 个 → 5、6、7、8。**一个 RTT 结束时刚好翻倍**。
- **一步到位法**：慢开始阶段 `cwnd = 初始值 + 本轮已成功确认的报文段数`。例：从 1 开始，累计成功发送并确认了 7 个 MSS → cwnd = 1+7 = 8；累计 10 个 → cwnd = 11。
- 分阶段核算法：1 个 + 2 个 + 4 个 = 7 个（三个 RTT 后 cwnd=8），再发 3 个够 10 个 → cwnd = 8+3 = 11。两种算法结果必须一致。

**同时考虑接收窗口时**：每个 RTT 后 rwnd 要减去本轮实际发出的数据量，发送窗口取两者较小值；若 rwnd 先降到 0，则无论 cwnd 多大都发不出去。

### 十三、UDP 与 TCP 对比总表

| 比较项 | UDP | TCP |
|---|---|---|
| 连接 | **无连接**，直接封装发送 | **面向连接**，三次握手建立、四次挥手释放 |
| 可靠性 | **不可靠**：出错/丢失直接丢弃，不确认、不重传、不排序 | **可靠**：无差错、不丢失、不重复、有序；确认 + 重传 + 排序 |
| 首部长度 | **8 B**（固定） | **20 B** 固定，最长 60 B |
| 开销 | 小：8 B 首部，无连接状态、无缓存、无计时器、无拥塞控制 | 大：20 B 首部 + 两端缓存 + 计时器 + 确认机制 + 拥塞控制 |
| 数据传输单位 | 面向**报文**，保留应用报文边界（教材补充） | 面向**字节流**，无边界，按字节编号 |
| 通信方式 | 一对一/一对多/多对多，支持广播多播 | 仅一对一，全双工 |
| 流量/拥塞控制 | 都没有 | rwnd 流量控制 + cwnd 拥塞控制 |
| 适用场景 | 视频会议、IP 电话、流媒体、DNS、广播（实时性 > 准确性） | 文件传输、网页、电子邮件、远程登录（准确性 > 实时性） |
| 相同字段 | 源端口、目的端口、校验和（均 16 位） | 同左 |

## 老师强调的考点

1. **TCP 是全章重中之重**——"选择题起码有十几道"，课后题数量就能看出重要性。选择 + 大题双线考。
2. **序号、确认号的含义**——"虽然简单，但是这一小节特别重要的内容，题目出现频率比较高"。选择高频，也是大题地基。
3. **三次握手、四次挥手必须能默写**——"这个是很核心的""可以尝试默写一下，后面很多题目都是基于这个"。选择 + 大题。
4. **TIME-WAIT 等 2MSL 的原因**——"这个很关键，考试出现过好几次"。简答/选择都可能。
5. **释放连接耗时：客户 1 RTT + 2MSL，服务器 1.5 RTT**——"这个点也出过好几次"。
6. **第二次和第三次挥手可以合并**——"大题的小问包括选择题都用得着"。
7. **拥塞控制四阶段的名称、含义、图**——"这一块最难的任务不是理解，是记住那几个名词""这个图一定要多看一看"。**必考大题**，其中"慢开始每收一个 ACK 加 1"这个小问"很多人容易出问题"。
8. **发送窗口 = min(接收窗口, 拥塞窗口)**——"题目中同时出现拥塞窗口和接收窗口，发送窗口由两者最小值决定"。
9. **3 个冗余 ACK 触发快重传**——选择常考，注意"第一个 ACK 不算冗余"。
10. **UDP 首部 8 B、TCP 20 B、IP 20 B**——"有一年考过，得自己知道"。
11. **UDP 校验和**——24 年考过一次选择题，属于"很偏"的点，规则要会。
12. **前两次握手不携带数据但消耗序号、FIN 消耗序号**——"真题一般就是不让它携带数据"，计算题必用。

## 快速技巧与口诀

**1. 序号三式（写在草稿纸最上面）**

```text
末字节 = 起始 + 长度 − 1
下一段起始 = 起始 + 长度
本段起始 = 上一段起始 + 上一段长度
```

**2. 握手/挥手默写模板**（字母随便换，结构不能错）

```text
三次握手：SYN=1,seq=x  →  SYN=1,ACK=1,seq=y,ack=x+1  →  ACK=1,seq=x+1,ack=y+1
四次挥手：FIN=1,seq=u  →  ACK=1,seq=v,ack=u+1  →  FIN=1,ACK=1,seq=w,ack=u+1  →  ACK=1,seq=u+1,ack=w+1
```

记法：**有确认号就必须 ACK=1**；**握手前两次 SYN=1**；**挥手第一、三次 FIN=1**；挥手第 3 次 `ack` 不变（A 没再发数据）、`seq` 变了（B 中间发过数据）。

**3. 拥塞控制画图法**（10 秒出答案）

- 横轴一个"波浪线"= 1 个 RTT，左侧标 cwnd，下方标 rwnd；
- 阈值前 ×2，阈值后 +1；
- 遇超时：cwnd 写 1，ssthresh 写"当前 cwnd ÷ 2"；
- 遇三冗余 ACK：cwnd 直接写"当前 cwnd ÷ 2"，**不写 1**；
- 每轮结束用 min(cwnd, rwnd) 决定实际发多少，rwnd 相应扣减。

**4. 一步到位法**

慢开始期间 `cwnd = 1 + 已确认报文段数`；若题目说"成功发送了 n 个 MSS"，直接 1+n（未超阈值时）。

**5. 释放时间公式**

```text
主动关闭方 = 1 RTT + 2 MSL
被动关闭方 = 1.5 RTT
```

**6. 审题三问**

题目给的/问的是 **cwnd**、**rwnd** 还是**发送窗口**？三者不同，问 cwnd 就不能答 min。

## 易错点与坑

1. **把序号当报文段序号**。长度 200、起始 100 的段，末字节是 **299**，下一段起始是 **300**；写成 300/301 全错。TCP 是"一字节一号"，链路层才是"一帧一号"。
2. **确认号理解反了**。确认号 N 表示"N−1 及以前都收到"，不是"最后收到的是 N"。收齐 100~299 后应回 **300**。
3. **数据偏移单位记成 8 字节**。TCP 数据偏移单位 **4 B**（最大 60 B）；IP 片偏移单位才是 **8 B**。
4. **小写 ack 与大写 ACK 混淆**。ack 是 32 位确认号字段，ACK 是 1 位标志；**ACK=1 时 ack 才有效**。写握手报文时"有 ack 就必须带 ACK=1"。
5. **以为慢开始是每个 RTT 瞬间翻倍**。实际是**每收到一个 ACK 加 1**，一个 RTT 累计才翻倍；一步到位算是 `1 + 确认个数`。
6. **ssthresh 减半减错对象**。减的是**拥塞发生时的 cwnd**，不是原 ssthresh。ssthresh=16、cwnd 涨到 24 时拥塞 → 新阈值 12，不是 8。
7. **快恢复把 cwnd 写成 1**。三个冗余 ACK → cwnd = 新 ssthresh（跌一半）；只有**超时**才 cwnd=1。
8. **三个窗口混用**。cwnd 是网络能力、rwnd 是接收能力、发送窗口是二者最小；题目问"拥塞窗口"却答发送窗口直接零分。
9. **忘记 SYN/FIN 各消耗一个序号**。例 54：首序号 1000，第三次握手 seq=1001 开始带数据，FIN seq=5001，则数据是 1001~5000 共 **4000 B**，不是 4001 或 5001。
10. **TIME-WAIT 认错主体**。TIME-WAIT 由**主动关闭方**进入；等 2MSL 是为了"最后一个 ACK 丢失后还能再回一次"。
11. **以为挥手一定四次**。第 2、3 次可合并为三次挥手（B 无数据要发时）。
12. **窗口扣减漏算在途数据**。课后 57：已发 200 B 未确认，通告窗口 500，则还能发 500−200=300 B，不是 500 B。
13. **发送序号与上次确认号冲突时的处理**。若"上次发的下一序号 701" ≠ "对方回的确认号 501"，说明旧数据未被确认，**按自己的序号 701 续发**，不能倒退重发 501（未超时就不重传）。
14. **UDP 长度与 IP 首部长度混淆**。UDP 长度 = 首部 + 数据（最小 8）；IP 首部长度只算首部。
15. **UDP 校验和忘记取反 / 忘记进位回卷**。最高位进位要加到最低位，最后必须按位取反；干扰项就是"没取反"的结果。
16. **RTT 与 MSL 单位不统一**。例 59：RTT=50 ms、MSL=800 ms，则 50+1600=**1650 ms**；例 60 里 4 RTT 是毫秒级、2MSL 是秒级，最后要换算成 60.04 s 这种形式。

## 本章例题

**例 1（课后 16，24 年真题）UDP 校验和**
题干给出 UDP 校验和计算过程中的中间结果，要求再与下一个 16 位字相加并写出最终校验和。
步骤：
1. 按 16 位一组做二进制反码求和，最高位进位回卷到最低位；
2. 得中间和 0x0FBC；
3. 按位取反 → 0xF043；
4. 验算 0x0FBC + 0xF043 = 0xFFFF，说明接收方校验必为全 1。
答案：**C（1111 0000 0100 0011）**。

**例 2（课后 46）序号反推**
甲已与乙建立连接，连续发 3 个报文段，长度分别为 300、400、500 B，第三段的序号是 900。乙仅正确接收第 1、3 段，问乙的确认号。
步骤：
1. 第三段 900~1299（900+500−1）；
2. 第二段末字节 = 900−1 = 899，长度 400 → 第二段 500~899；
3. 第一段末字节 = 500−1 = 499，长度 300 → 第一段 200~499；
4. 第 1 段收到、第 2 段丢失、第 3 段收到，但 TCP 必须**按序**交付，500 没到就不能确认 900；
5. 确认号 = 期望收到的下一个字节 = **500**。
答案：**500**。

**例 3（课后 54）握手/挥手消耗序号**
甲、乙建立连接，甲的第一个序号是 1000，甲发完数据后发 FIN，seq=5001。问甲共发了多少字节数据。
步骤：
1. 第 1 次握手 seq=1000，消耗 1 个序号但不带数据；
2. 第 3 次握手 seq=1001，可携带数据，数据从 1001 开始；
3. FIN seq=5001 消耗 1 个序号，不带数据，数据到 5000 为止；
4. 字节数 = 5000 − 1001 + 1 = **4000 B**。
答案：**4000 B**。

**例 4（课后 57）确认号与窗口扣减**
甲向乙发 `seq=501、长度 200` 的段（501~700），乙回 `ack=501、rwnd=500`。问甲下一步从哪发、能发多少。
步骤：
1. ack=501 说明 501~700 尚未被确认（否则应回 701）；
2. 未超时 → 不重传，按自己的序号续发，下一段从 **701** 开始；
3. 已发出的 200 B 仍占用窗口，可用窗口 = 500 − 200 = **300 B**；
4. 可发 701~1000，共 300 B。
答案：**从 701 开始，最多发 300 B（到 1000）**，选 B。
（若把题干的 ack 改成 701，则说明 501~700 已收到，窗口未占用，可从 701 发满 500 B 到 1200。）

**例 5（课后 51）快重传 vs 超时重传**
T0 收到 ack=100，发出 100~199 的段后丢失；随后发出的 200、300、400 段均到达，接收方三次回 ack=100。
步骤：
1. 第 1 个 ack=100 是正常确认，后 3 个是冗余 ACK；
2. 收到第 3 个冗余 ACK → 立即重传，时刻 **T3**；
3. 若只依赖计时器 → **T4** 超时重传。
答案：**支持快重传在 T3，采用超时重传在 T4**。

**例 6（课后 43）超时后的 cwnd**
某连接发生超时，超时后经过 4 个 RTT，问拥塞窗口。
步骤：
1. 超时 → ssthresh = 拥塞时 cwnd 的一半。本题拥塞时 cwnd=16 → ssthresh=8；
2. cwnd 重置为 1，执行慢开始；
3. 第 1~4 个 RTT 结束时 cwnd 依次为 2、4、8、9（第 3 个 RTT 到阈值 8，之后每 RTT 只 +1）。
答案：**cwnd = 9 MSS**。

**例 7（课后 48）发送窗口**
连接刚建立（cwnd=1），某时刻超时（此时 cwnd=8），此后不再超时，再经过 10 个 RTT。接收窗口恒为 10。问最后发送窗口。
步骤：
1. 超时 → ssthresh = 8/2 = 4，cwnd = 1；
2. 第 1~10 个 RTT 结束时 cwnd 依次为：2、4（到阈值）、5、6、7、8、9、10、11、**12**；
3. rwnd 始终 10；
4. 发送窗口 = min(12, 10) = **10**（选 A）。
（本题即使不算也能选：发送窗口永远不可能超过接收窗口 10。）

**例 8（课后 49）cwnd 与 rwnd 同时变化**
刚建立连接，cwnd=1，ssthresh=32，MSS=1 KB，接收缓存 16 KB。经过 4 个 RTT 均未超时，问此时能发多少。
步骤：

| RTT | 起始 cwnd | 实际发送 | 结束 cwnd | 剩余 rwnd |
|---|---|---|---|---|
| 1 | 1 | 1 | 2 | 15 |
| 2 | 2 | 2 | 4 | 13 |
| 3 | 4 | 4 | 8 | 9 |
| 4 | 8 | 8 | 16 | 1 |

1. cwnd 未到阈值 32，一直翻倍：1→2→4→8→16；
2. rwnd 逐轮扣减：16→15→13→9→1；
3. 发送窗口 = min(16, 1) = **1 MSS = 1 KB**。
答案：**下一轮只能发 1 KB**。

**例 9（课后 59）释放连接耗时**
RTT=50 ms，MSL=800 ms，客户端主动断开。
步骤：
1. 客户机：1 RTT + 2MSL = 50 + 2×800 = **1650 ms**；
2. 服务器：1.5 RTT = 75 ms。
答案：**客户端 1650 ms，服务器 75 ms**。

**例 10（课后 60）全流程综合（重点星号题）**
主机向服务器发送 3000 B 数据，MSS=1000 B，RTT=10 ms，MSL=30 s，从建立连接算到进入 CLOSED，最快多久。
步骤：
1. 第 1、2 次握手不携带数据 → 1 个 RTT；
2. 第 3 次握手携带第 1 个报文段（1000 B），服务器回 ACK，同时 cwnd 由 1 涨到 2 → 第 2 个 RTT；
3. cwnd=2，一次发 2 个报文段（2000 B），3000 B 发完 → 第 3 个 RTT；
4. 释放连接一来一回 → 第 4 个 RTT；
5. 主动关闭方再等 2MSL = 60 s。
合计：4 RTT + 2MSL = 40 ms + 60 s = **60.04 s**。
（此题把三次握手、慢开始、四次挥手、2MSL、状态迁移全串起来，是"知识点旧、考法新"的典型压轴选择。）

## 知识点详解

### 一、C/S 与 P2P 模型（6.1）

| | C/S（客户/服务器） | P2P（对等） |
|---|---|---|
| 地位 | 不平等：服务器提供服务，客户请求服务 | 对等，每个节点既是客户也是服务器 |
| 通信 | **客户之间不直接通信**，都要经服务器中转 | 节点之间可直接通信 |
| 可靠性 | 服务器是单点，**服务器坏了全网瘫** | **健壮性强**，一个节点失效不影响其他节点 |
| 负载 | 全部压在服务器上 | 分散到各节点，**减轻服务器压力** |

老师给的现实例子：微信客户端只是客户，数据都存在服务器；服务器一崩，所有人都用不了。P2P 则像多个客户端直接互传，不必先绕服务器。

考法极浅：19 年考过一次，"P2P 是对等关系"对，"C/S 中客户直接通信"错——错误选项都很明显。

### 二、DNS 的层次与查询（6.2，书 266~269 页）

DNS 的唯一职责：**把域名转换成 IP 地址**。因为人记不住 32 位 IP，但通信必须用 IP。DNS **基于 UDP**，端口 53。

**域名结构**（从右往左级别降低）：

```text
www . abc . xyz . com .
 ↑     ↑     ↑     ↑
主机  三级  二级  顶级（com 表示商业机构，cn 表示中国，edu 表示教育）
```

**四类域名服务器**：

| 类型 | 作用 |
|---|---|
| 根域名服务器 | 知道**所有顶级域名服务器**的域名和 IP；任何查询的第一站（迭代时） |
| 顶级域名服务器 | 管理该顶级域下的所有二级域，知道其权限域名服务器在哪 |
| **权限域名服务器** | 保存某区的完整数据，**总能完成"主机名 → IP"的最终转换** |
| 本地域名服务器 | 主机配置的默认 DNS，先查它；它有缓存 |

**两种查询方式**：

```text
【递归查询】主机把活全托给本地，本地再层层托付，结果原路返回
  主机 → 本地 → 根 → 顶级 → 权限
  主机 ← 本地 ← 根 ← 顶级 ← 权限        （一路深到底，像 DFS）

【迭代查询】本地自己跑腿，每问一次只拿到"下一站地址"
  本地 → 根       根回："去问 com 顶级"
  本地 → com顶级  顶级回："去问 xyz 权限"
  本地 → xyz权限  权限回："去问 abc 权限"
  本地 → abc权限  权限回："IP 是 …"
```

**关键结论（选择题必考）**：

- **主机 → 本地域名服务器，一定是递归**。因为主机只发一次请求，本地折腾一大圈后把最终结果返回给它。
- **本地域名服务器 → 根/顶级/权限，可以递归也可以迭代**，题目会明说。
- 递归是"你帮我查完"，迭代是"你告诉我下一步问谁"。

**缓存**：主机和本地域名服务器都缓存最近解析过的域名，靠**局部性原理**——常用的先存起来。所以"最少查询次数"往往不是 1 而是 **0**（本地已有缓存）。

### 三、FTP（6.3，书 270 页）

FTP 用于传文件，C/S 模型，**基于 TCP**（文件不能出错）。最大的特点是**控制连接与数据连接分离**（带外控制）：

| 连接 | 端口 | 生存期 | 传什么 |
|---|---|---|---|
| **控制连接** | 服务器 **21** | **整个会话期间一直保持打开** | 命令、响应（"我要下载 xx 文件"） |
| **数据连接** | 服务器 **20** | **每次数据传输完毕立即关闭** | 真正的文件内容 |

- 端口不用死记，只需知道**都是服务器的端口**（0~1023 是服务器熟知端口），题目说"客户端 22 端口"就是错的。
- 控制连接先建立，贯穿始终；每传一个文件就新开一条数据连接，传完即关。

### 四、电子邮件系统（6.4，书 272~275 页）

三个组成部分：**用户代理（UA）**、**邮件服务器**、**协议**。最常见的协议是 SMTP 和 POP3。

```text
  发件人 UA  --SMTP-->  发送方邮件服务器  --SMTP-->  接收方邮件服务器  --POP3-->  收件人 UA
             (推送)                              (推送)                  (拉取)
```

| 协议 | 方向 | 作用 | 基于 |
|---|---|---|---|
| **SMTP** | 推送（push） | UA → 发送方服务器；发送方服务器 → 接收方服务器 | TCP |
| **POP3** | 拉取（pull） | 接收方服务器 → 收件人 UA | TCP |
| **IMAP**（教材补充） | 拉取 | 收件人 UA 访问服务器上的邮件，邮件保留在服务器，可只下载首部 | TCP |

**SMTP 的局限**：只能传送 **7 位 ASCII 码**，汉字、图片、可执行文件都传不了。**MIME** 在 SMTP 之上做扩展，把这些内容编码成 ASCII 再传——**MIME 并没有取代 SMTP，仍基于 SMTP**。

**Web 邮箱的变化**：在网页上写信发信时，用户代理 → 发送方邮件服务器这一段用 **HTTP**；邮件服务器之间**仍然是 SMTP**。

考法：只考"哪一段用哪个协议"，四道选择题都很浅。18 年之后再没考过。

### 五、WWW 与 HTTP 的基本性质（6.5，书 285~287 页）

- **URL（统一资源定位符）**：唯一标识网络上的一个资源（网页、图片、视频都算资源）。
- **HTTP**：应用层协议，**基于 TCP**。
- **HTTP 是无连接的**：这是**站在应用层视角**说的——HTTP 自己不发握手报文，直接发请求；连接由下层的 TCP 保证。别理解成"不需要 TCP 连接"。
- **HTTP 是无状态的**：服务器不记得你上次来过，同一页面任何时间打开都一样。
- **Cookie**：弥补无状态。服务器给浏览器一小段数据，浏览器之后每次请求都带上，用来记录用户特征、浏览记录、购物车等，实现"跟踪用户活动"。

**一次完整访问的流程（顺序不能颠倒）**：

```text
① 浏览器从 URL 中取出域名 → DNS 解析得到 IP 地址
② 用该 IP 与服务器建立 TCP 连接（三次握手）
③ 浏览器发送 HTTP 请求报文（GET /index.html HTTP/1.1）
④ 服务器返回 HTTP 响应报文（状态行 + 首部 + 网页数据）
⑤ 浏览器解析 HTML，对其中的图片/CSS/JS 再发请求
⑥ 数据传输完毕后释放 TCP 连接（HTTP/1.1 可保持连接复用）
```

**为什么必须先 DNS 再 TCP**：三次握手在传输层，但建连接必须知道对方 IP，只有域名无法定位主机。

**报文结构**（了解即可，408 不深考）：

```text
请求：GET /index.html HTTP/1.1      ← 请求行（方法、URL、版本）
      Host: www.abc.edu.cn          ← 首部行
      Connection: keep-alive        ← 持续连接；写 close 则是非持续
      Cookie: …
      （空行）实体

响应：HTTP/1.1 200 OK
      Content-Type: text/html
      （空行）网页内容
```

常见状态码：200 成功、404 找不到页面、403 禁止访问、502 网关错误（只需认得 404）。

### 六、持续连接、非持续连接与 RTT 计算（6.5.2）

| 版本 | 默认方式 | 特点 |
|---|---|---|
| HTTP/1.0 | **非持续连接** | **每个对象都要单独建立一个 TCP 连接**，用完就关 |
| HTTP/1.1 | **持续连接** | 建立一次连接，后续所有对象都复用这条连接 |

持续连接又分两种：

- **非流水线**：必须**收到前一个响应**才能发下一个请求（串行，一次一个）；
- **流水线**：可以**连续发出多个请求**，响应按序回来（并发，一次一批）。

**RTT 计算公式**（教材补充，课程用例题讲的就是这套）：

设基础页面 1 个、内嵌引用对象 N 个，忽略传输时延和排队时延，每个对象都很小（1 个 RTT 内传完）：

| 方式 | 需要的 RTT | 推导 |
|---|---|---|
| 非持续连接（串行） | **2(N+1)** | 基础页面：1 RTT 建 TCP + 1 RTT 请求/响应；每个对象再各 2 RTT |
| 持续 + 非流水线 | **N+2** | 建连 1 + 基础页面 1 + N 个对象各 1 |
| 持续 + 流水线 | **3** | 建连 1 + 基础页面 1 + 所有对象一起请求/响应 1 |

**N=5 的算例**：

| 方式 | 计算 | 结果 |
|---|---|---|
| 非持续 | 2×(5+1) | **12 RTT** |
| 持续非流水线 | 5+2 | **7 RTT** |
| 持续流水线 | 3 | **3 RTT** |

注意：若题目说"**并行**建立 N 个 TCP 连接"，非持续也可压缩为 2 RTT（建连并行 1 + 请求响应 1），但这属于变形，题干会明说。

## 老师强调的考点

1. **本章最重要是 HTTP 和 DNS**——"这里面最重要的就是 HTTP 和 DNS，大家要有一个主次，其他几个其实考得都特别浅"。
2. **DNS 的递归/迭代图"经常考"**——"269 页这个图就要重点画一下，我们这边经常考这个图"。选择高频。
3. **HTTP 版本号要记**——"1.1 默认是持续连接，1.0 是非持续连接"，"版本号最好稍微记一记"。
4. **综合计算题是压轴**——DNS + TCP 三次握手 + HTTP 串起来算 RTT，"这种题目一般都是压轴题，第一遍做不出来很正常"。选择。
5. **应用层不单独出大题**——"不会说单独为了第六章出一个大题，有大题的话会和前面章节综合去考"，通常只占一个小问。
6. **FTP 的控制连接/数据连接**——控制连接整个会话保持、数据连接每次传完就关；"考的都是服务器的端口，不需要记 20/21"。
7. **邮件三个协议的分工**——"你记一下协议的名称就行"，SMTP 推、POP3 拉，服务器之间还是 SMTP。
8. **MIME 与 SMTP 的关系**——SMTP 只能传 7 位 ASCII，特殊内容用 MIME，"MIME 也是基于 SMTP 的"。
9. **HTTP 无连接是应用层视角**——"它本身这个应用层无连接，但是传输层还是需要建立连接的"。
10. **C/S 与 P2P 只考过一次（19 年）**——了解特点即可。

## 快速技巧与口诀

**1. 访问网页的顺序口诀**

```text
"先解析、再握手、后请求、末释放"
DNS → TCP 三次握手 → HTTP 请求 → HTTP 响应
```

任何综合题先按这个骨架列时间轴，再往每段填 RTT。

**2. DNS 查询次数速算**

- 最少：**0 次**（本地域名服务器有缓存）；
- 最多（迭代）：**1（根）+ 1（顶级）+ 权限服务器级数**；
- 权限服务器级数 = 顶级域名左边还有几级。`www.abc.xyz.com` → 顶级 com，权限 xyz、abc，共 **4 次**；`www.abc.com` → 共 **3 次**。

**3. HTTP 连接方式速记**

```text
1.0 非持续：一个对象一条连接 → 2(N+1) RTT
1.1 持续非流水线：一条连接排队发 → N+2 RTT
1.1 持续流水线：一条连接一起发 → 3 RTT
```

**4. 邮件协议方向记法**

"**发用 SMTP，收用 POP3**"；SMTP 是"推"（push），POP3/IMAP 是"拉"（pull）。服务器之间永远 SMTP。

**5. FTP 记法**

"**21 管命令不断线，20 传数据传完就断**"。

## 易错点与坑

1. **以为 DNS 基于 TCP**。DNS 查询默认 **UDP 53**；只有区域传送等少数场合用 TCP（教材补充）。
2. **递归/迭代主体搞反**。主机 → 本地**必为递归**；本地 → 根/顶级/权限才可能是迭代。看到"主机采用迭代"直接排除。
3. **DNS 最少次数答 1**。本地有缓存时最少是 **0 次**，不是 1 次。
4. **权限域名服务器级数漏算**。`www.abc.xyz.com` 有两级权限服务器，最多查 4 次；只算到 com 会误选 3 次。
5. **非持续连接只算 N 个 RTT**。每个对象要"建 TCP 1 RTT + 请求响应 1 RTT"= 2 RTT，还要加基础页面的 2 RTT，共 2(N+1)。
6. **流水线与非流水线混淆**。非流水线必须收到前一个响应才发下一个请求（N+2）；流水线一次性发完（3 RTT）。
7. **把 HTTP 的"无连接"当成"不用 TCP"**。HTTP 无连接是无状态语义层面的说法，传输层仍要先三次握手。
8. **FTP 控制连接与数据连接的生存期写反**。控制连接**不断**，数据连接**传完即断**。
9. **FTP 端口主体错**。21/20 都是**服务器**端口，题目说"客户端 21 端口"是错的。
10. **收邮件写成 SMTP**。SMTP 只负责"推"到接收方服务器；用户取信是 POP3/IMAP。
11. **SMTP 能传汉字**。不能，只能 7 位 ASCII，汉字要靠 MIME 编码。
12. **例 18 型综合题漏掉拥塞窗口限制**。图片 3 MSS 不能在 1 个 RTT 内发完：首次 cwnd=1，之后 2、4，必须拆成 2 个 RTT。
13. **忘记"第三次握手可携带请求"**。算 RTT 时握手只算 1 个 RTT，请求搭在第三次握手上，不再另加。
14. **单位混淆**。RTT 给的是 ms，2MSL 可能给的是 s，最后要统一（如 40 ms + 60 s = 60.04 s）。

## 本章例题

**例 1（真题 12）迭代查询次数**
某主机解析 `www.abc.xyz.com`，采用迭代查询，问本地域名服务器最少、最多查询多少次。
步骤：
1. 最少：本地域名服务器已有该域名缓存 → **0 次**；
2. 最多：先问根（回"去问 com"）→ 问 com 顶级（回"去问 xyz"）→ 问 xyz 权限（回"去问 abc"）→ 问 abc 权限（回 IP）；
3. 共 1 + 1 + 2 = **4 次**。
答案：**最少 0 次，最多 4 次**（不是 3 次，因为权限服务器有两级）。

**例 2（真题 14）DNS + TCP + HTTP 综合**
主机点击链接访问某页面，采用递归+迭代方式解析域名，局域网与互联网的 RTT 均为 10 ms，其他时延忽略。域名只有一级权限服务器。求从点击到收到页面的最短、最长时间。
步骤：
1. **DNS**：最少 0 RTT（有缓存），最多 3 RTT（根、顶级、权限各一次）→ 0~30 ms；
2. **TCP 三次握手 + HTTP 请求/响应**：第三次握手携带请求，服务器回响应，共 1 RTT（握手）+ 1 RTT（请求响应）= 2 RTT → 20 ms；
3. 合计：最少 0+20 = **20 ms**，最多 30+20 = **50 ms**。
答案：**20 ms ~ 50 ms（选 D）**。
（若域名有两级权限服务器，DNS 最多 4 RTT，总时间上限要再加 10 ms。）

**例 3（真题 18）持续连接 + 拥塞控制（压轴）**
页面大小 1 MSS，内嵌图片 3 MSS，RTT=10 ms，域名解析已完成，HTTP/1.1 持续连接。求从请求建连到收完所有内容的时间。
步骤：
1. 三次握手（第三次携带 HTTP 请求）：**1 RTT**，此时服务器 cwnd=1；
2. 服务器发基础页面 1 MSS：**1 RTT**，cwnd 由 1 涨到 2；
3. 请求图片，服务器本轮只能发 2 MSS：**1 RTT**，cwnd 由 2 涨到 4；
4. 还剩 1 MSS，下一轮发完：**1 RTT**；
5. 合计 4 RTT = 4×10 = **40 ms**。
答案：**40 ms**。
（本题的"坑"是要想到 TCP 慢开始限制了服务器一次能发多少，不能假设 3 MSS 一次发完。）

**例 4（真题 19，课下做）HTTP/1.0 非持续**
条件同例 3（基础页面 1 MSS、图片 3 MSS、RTT=10 ms），但版本为 HTTP/1.0，每个对象都要新建 TCP 连接。问总时间。
步骤：
1. 基础页面：建连（第三次握手带请求）1 RTT + 服务器发 1 MSS 1 RTT = **2 RTT**；
2. 图片另开一条连接：建连+请求 1 RTT；新连接 cwnd 从 1 开始，先发 1 MSS（1 RTT）；cwnd=2，再发剩余 2 MSS（1 RTT），共 **3 RTT**；
3. 合计 5 RTT = **50 ms**。
通用结论：若不考虑慢开始（默认每个对象 1 RTT 内传完），N 个引用对象共 **2(N+1) RTT**；N=3 时为 8 RTT = 80 ms。核心是把"每个对象重新三次握手"算进去，这正是 1.1 持续连接要解决的问题。
