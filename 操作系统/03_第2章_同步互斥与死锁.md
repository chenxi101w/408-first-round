## 知识点详解

### 一、同步与互斥的基本概念（2.3.1）

#### 1. 互斥：不能同时发生

**定义**：两个或多个进程因争用同一资源，**在同一时刻只能有一个进程使用**，这种制约关系叫互斥。

课上例子（直接背）：Word 打印文件 F1，WPS 打印文件 F2，后台各是一个进程，共用一台打印机。若同时打印，一张纸上会**既有 F1 的内容又有 F2 的内容**，输出错乱。所以不同进程使用打印机必须互斥。

**互斥是"间接制约"**：两个进程本身没有逻辑上的先后要求，只是因为抢同一个资源才被迫排队。

#### 2. 同步：强行规定先后次序

**定义**：为完成某项任务而建立的多个进程，需要**按约定的先后次序执行**，这种制约叫同步（直接制约）。

课上例子：
- 操作系统具有**异步性**：P1、P2、P3 谁先谁后不确定，可能 1-3-2，也可能 2-3-1。若要求"P1 完成后立刻 P2，P2 完成后立刻 P3"，这个顺序就是同步关系。
- 表达式 `1 + 2 × 3`：乘法进程先算 `2×3`，加法进程才能算 `1+6`。不加限制，加法可能先执行，结果错。

**一句话区分**：同步 = 有先后顺序要求；互斥 = 不许同时干。

#### 3. 临界资源与临界区

| 术语 | 定义 | 例子 |
|---|---|---|
| 临界资源 | **一个时刻仅允许一个进程访问**的资源 | 打印机（硬件）、多个进程共享的变量（软件） |
| 临界区 | **访问临界资源的那段代码**（是代码，不是资源） | P1 中用打印机的那几行、P2 中用打印机的那几行 |

要点：不同进程的临界区**不能同时执行**，同一时刻只允许一个进程进入临界区。注意临界区本质是"代码段"，判断某段是不是临界区，看它**是否访问了临界资源**。

#### 4. 临界区的四区结构（必画）

以共享标志变量 `flag`（`false` = 无人使用）为例：

```
while (true) {
    进入区：检查 flag，若为 false 则置 flag = true（上锁）   ← 检查 + 设置标志
    临界区：访问临界资源（用打印机）
    退出区：把 flag 置回 false（解锁）                        ← 清除标志
    剩余区：其余不需要互斥的代码
}
```

流程：P1 在进入区看到 `flag=false` → 置 `true` → 进临界区；此时 P2 在进入区看到 `flag=true` → **停在进入区等待**；P1 用完在退出区清零，P2 才可能进。

#### 5. 临界区管理的四个原则（逐条解释）

| 原则 | 含义 | 违反后果 | 地位 |
|---|---|---|---|
| **空闲让进** | 临界区空闲时，请求进入的进程应**立即被允许进入**，不得无故拖延 | 资源白白闲置，利用率低 | 必须 |
| **忙则等待** | 已有进程在临界区内，其他试图进入的进程**必须等待** | 两个进程同时进 → 数据错乱，互斥失效 | 必须（互斥的实质） |
| **有限等待** | 请求进入的进程应在**有限时间内**获准进入，不能无限期等 | 饥饿 | 必须 |
| **让权等待** | 进程不能进入临界区时，应**立即释放 CPU 进入阻塞态**，不能"忙等" | CPU 空转浪费（盲等） | 原则上应遵循，**非必须** |

老师强调的两点：
1. **前三个是"实现互斥"必须的，让权等待不是必须的**。因为核心目标是互斥：哪怕 P1 抱着 CPU 原地空转，只要它没进临界区，互斥照样成立，只是浪费 CPU。
2. **盲等（忙等待）**：进程占着 CPU 反复测试 `while(flag)`，不让出 CPU，就是违反让权等待的典型表现。

#### 6. 与进程状态转换的联系

打印机分给 B，A 申请打印机失败 → A 从**运行态变阻塞态**；B 用完释放打印机 → **唤醒 A**，A 从**阻塞态变就绪态**，再被调度才能运行。这条链是 2.1 状态转换在 2.3 的落地考法。

### 二、临界区互斥的软件与硬件实现（教材补充，课上明确跳至强化）

> 老师原话：这一块"很琐碎、不难、很吃记忆"，只考零星选择题，留到 6 月强化再补。以下按教材补全，**判断表是选择题重灾区**。

#### 1. 单标志法（违背"空闲让进"）

```c
int turn = 0;                 // turn 表示"当前轮到谁进"

P0:  while (turn != 0);       // 不是自己就等
     临界区;
     turn = 1;
     剩余区;

P1:  while (turn != 1);
     临界区;
     turn = 0;
     剩余区;
```

问题：P0 进一次后把 `turn` 置 1，若 P1 一直不想进，P0 **第二次想进也进不去**——临界区明明空闲却被挡在门外，违背**空闲让进**。两个进程必须严格交替进入。

#### 2. 双标志法——先检查（违背"忙则等待"）

```c
bool flag[2] = {false, false};   // flag[i] = Pi 想进/正在临界区

P0:  while (flag[1]);            // 先检查对方
     flag[0] = true;             // 再置自己的标志
     临界区;
     flag[0] = false;

P1:  while (flag[0]);
     flag[1] = true;
     临界区;
     flag[1] = false;
```

问题：P0 检查到 `flag[1]=false` 后**被切换**，P1 检查到 `flag[0]=false`，两者都通过检查、都置标志、**同时进入临界区**——违背**忙则等待**。

#### 3. 双标志法——后检查（违背"空闲让进"，可能饥饿）

```c
P0:  flag[0] = true;             // 先表明自己想进
     while (flag[1]);            // 再检查对方
     临界区;
     flag[0] = false;

P1:  flag[1] = true;
     while (flag[0]);
     临界区;
     flag[1] = false;
```

问题：P0、P1 同时置 `true`，再互相检查，**谁也进不去**，互相谦让到死——违背**空闲让进**与**有限等待**（可能长期僵持，属于饥饿）。

#### 4. Peterson 算法（前三个原则都满足）

```c
bool flag[2] = {false, false};
int turn = 0;

P0:  flag[0] = true;                  // 我想进
     turn = 1;                        // 但先让对方进（谦让）
     while (flag[1] && turn == 1);    // 对方想进 且 轮到我让 → 等
     临界区;
     flag[0] = false;

P1:  flag[1] = true;
     turn = 0;
     while (flag[0] && turn == 0);
     临界区;
     flag[1] = false;
```

关键：`turn` 只能有一个值，**最后写 `turn` 的进程会让步**，所以不可能两个都进（忙则等待）、也不会两个都不进（空闲让进），且等待时间有界。仍是忙等，**不满足让权等待**。软件方法中唯一满足前三条的。

#### 5. 硬件方法

**（1）关中断（中断屏蔽）**

```c
关中断;        // 关中断期间不会发生进程切换
临界区;
开中断;
```

最简单，但**只适用于单处理机**（多核上其他核仍在跑），且关中断是特权指令，**只能在内核态**用。

**（2）TestAndSet（TSL，原子指令）**

```c
bool TestAndSet(bool *lock) {   // 一条指令完成"读旧值 + 置 true"
    bool old = *lock;
    *lock = true;
    return old;
}

// 进程代码
while (TestAndSet(&lock));      // 返回 true 说明锁已被占，继续自旋
临界区;
lock = false;                   // 解锁
剩余区;
```

**（3）Swap / XCHG（原子交换）**

```c
bool old = true;
do {
    Swap(&lock, &old);          // 原子交换：lock 与 old 互换
} while (old == true);          // 换回来的旧值是 true → 锁被占，继续自旋
临界区;
lock = false;
```

#### 6. 六种方法 × 四原则 判断表（背诵）

| 方法 | 空闲让进 | 忙则等待 | 有限等待 | 让权等待 | 主要缺陷 |
|---|:---:|:---:|:---:|:---:|---|
| 单标志法 | ✗ | ✓ | ✓ | ✗ | 强制轮转，一方不进另一方也进不去 |
| 双标志先检查 | ✓ | ✗ | ✗ | ✗ | 同时通过检查，同时进临界区 |
| 双标志后检查 | ✗ | ✓ | ✗ | ✗ | 同时置 true，互相谦让，都进不去（饥饿） |
| **Peterson** | ✓ | ✓ | ✓ | ✗ | 忙等（软件方法里最优） |
| 关中断 | ✓ | ✓ | ✓ | ✗ | 仅单 CPU、仅内核态 |
| TestAndSet | ✓ | ✓ | ✗* | ✗ | 忙等，无排队机制 |
| Swap | ✓ | ✓ | ✗* | ✗ | 同 TSL |

\* TSL/Swap 没有排队机制，理论上存在某进程反复抢不到锁的情况，教材对"有限等待"打叉；若题目只问"是否满足让权等待"，一律答**不满足**。

### 三、信号量机制（2.3.2，本节最核心）

#### 1. 原语与 PV

**原语**：执行过程中**不可被中断**的一段代码（要么全做，要么不做）。信号量的操作由两个原语构成：

- `wait(S)` = `P(S)`，表示**申请/消耗**一个资源；
- `signal(S)` = `V(S)`，表示**释放/增加**一个资源。

`P/V`、`wait/signal` 完全等价。**但题干写 `wait/signal` 时，答案也写 `wait/signal`**（老师强调的审题习惯）。

#### 2. 整型信号量（不满足让权等待）

```c
int S = 1;                       // S 表示可用资源数
wait(S)  { while (S <= 0); S = S - 1; }
signal(S){ S = S + 1; }
```

`while(S<=0);` 死循环空转 = **盲等**，占着 CPU 不放，违反让权等待。这是它被淘汰的原因。

#### 3. 记录型信号量（Dijkstra 提出，能实现让权等待）

```c
typedef struct {
    int value;              // 剩余资源数
    struct process *L;      // 等待队列（链式队列）队首指针
} semaphore;
```

```c
void wait(semaphore S) {          // P(S)
    S.value--;                    // 先申请：资源数减 1
    if (S.value < 0) {            // 减完变负 → 没资源了
        将当前进程插入 S.L 队尾;   // 进等待队列
        block();                  // 阻塞，主动放弃 CPU（实现让权等待）
    }
}

void signal(semaphore S) {        // V(S)
    S.value++;                    // 归还 1 个资源
    if (S.value <= 0) {           // 加完仍 <=0 → 说明还有人在等
        从 S.L 队首移出一个进程 P;
        wakeup(P);                // 阻塞 → 就绪
    }
}
```

**两个不等号是死考点**：P 里判 `value < 0`，V 里判 `value <= 0`。原因：P 是先减后判，V 是先加后判，边界错一位。

**信号量值的几何意义**（必背）：

| S.value | 含义 |
|---|---|
| `> 0` | 还有 `S.value` 个资源可用 |
| `= 0` | 资源刚好用尽，无人等待 |
| `< 0` | 有 `\|S.value\|` 个进程在等待该资源（还缺这么多） |

互斥实例推演（`mutex = 1`，P1/P2/P3 争临界区）：

| 时刻 | 动作 | mutex 值 | 结果 |
|---|---|---|---|
| t1 | P1 执行 P | 0 | 不小于 0，P1 进临界区 |
| t2 | P3 执行 P | −1 | 阻塞，入队 |
| t3 | P2 执行 P | −2 | 阻塞，入队 |
| t4 | P1 执行 V | −1 | ≤0，唤醒队首 P3 |
| t5 | P3 执行 V | 0 | ≤0，唤醒 P2 |

三个进程的临界区在时间上**恰好错开**，互斥成立。

#### 4. 信号量的定义式写法与初值口诀

```c
semaphore mutex = 1;     // 互斥信号量：临界区只有 1 个"名额"
semaphore empty = N;     // 同步信号量：初始有 N 个空闲缓冲区
semaphore full  = 0;     // 同步信号量：初始有 0 个产品
```

**判定口诀：`信号量初值 = 该资源的初始可用数量`。**

- 互斥问题：临界区就是"1 个资源"，所以 **mutex 恒为 1**；
- 同步问题：先发生的动作**还没发生**，它产生的资源当前为 0，所以 **初值通常为 0**；
- 若系统**初始就已经有该资源**（如信箱里已有 X 封信），初值就写 X，空位写 `容量 − X`（课后 21 题就考这个）。

**多个同类资源**：`初值 = 资源总数`。两台打印机、四个进程都申请，初值设 2，则前两个进程 P 完 value 为 1、0 不被阻塞，后两个变 −1、−2 被阻塞。

**不同临界区配独立信号量**：P1/P2 用打印机 1（`S1=1`），P3/P4 用打印机 2（`S2=1`）。若图省事只设一个信号量，会把本无关系的两组进程强行互斥，属**过度互斥**的错误。

#### 5. 用信号量实现互斥

```c
semaphore mutex = 1;
P1() { …; P(mutex); 临界区; V(mutex); … }
P2() { …; P(mutex); 临界区; V(mutex); … }
```

理解方式：**P = 加锁，V = 解锁**。进房间先锁门，别人进不来；出门开锁，别人才进。**PV 必须成对出现**，且夹住的只能是临界区。

#### 6. 用信号量实现同步（前 V 后 P）

规则：**先执行的动作后面加 V，后执行的动作前面加 P；初值 0。**

以"X 语句必须在 Y 语句之前"为例：

```c
semaphore S = 0;
X:  x 语句;  V(S);      // 先做→后面 V
Y:  P(S);    y 语句;    // 后做→前面 P
```

为什么成立：若调度器偏偏先跑 Y，`P(S)` 使 `S: 0 → −1 < 0`，Y **立即阻塞**；等到 X 执行完 `V(S)` 使 `S: −1 → 0 ≤ 0`，唤醒 Y。若调度器本来就先跑 X，则 X 的 V 把 S 加到 1，Y 的 P 减回 0，不阻塞，顺序自然正确。**无论谁先被调度，最终顺序都被强制成 X→Y**。

#### 7. 用信号量实现前驱关系

本质是同步。**每条前驱边设一个信号量，初值 0**；边的**起点**（先发生）在动作后 `V`，边的**终点**（后发生）在动作前 `P`。

课上例：A、B 在 C 之前；C、D 在 E 之前。

```c
semaphore a=0, b=0, c=0, d=0;      // 每条边一个
A: { A; V(a); }
B: { B; V(b); }
C: { P(a); P(b); C; V(c); }
D: { D; V(d); }
E: { P(c); P(d); E; }
```

`C` 前面有两个 P，因为 C 有两条入边，必须 A、B **都**完成；D 没有前驱，前面不加 P。

### 四、经典同步问题（2.3.3）

**通用解题四步**（老师给的流程）：① 关系分析（哪些互斥、哪些同步）→ ② 确定 PV 位置 → ③ 确定信号量**个数、含义、初值** → ④ 填入代码。其中个数、初值、含义、位置是**采分点**，多定义少定义都扣分。

#### 1. 生产者-消费者（模板，必须会默写）

模型：一组生产者、一组消费者，共享**初始为空、容量为 N** 的缓冲区，缓冲区是临界资源。

**关系分析**：
- 互斥：多生产者之间、多消费者之间、生产者与消费者之间，对缓冲区的访问都互斥；
- 同步：有空位才能放（empty），有产品才能取（full）。

```c
semaphore mutex = 1;    // 缓冲区互斥
semaphore empty = N;    // 空闲缓冲区个数
semaphore full  = 0;    // 已有产品个数

producer() {
    while (1) {
        produce_item();      // 生产产品（不需互斥）
        P(empty);            // ① 先申请空位——没有空位就在这里阻塞
        P(mutex);            // ② 再锁缓冲区
        put_item();          // 放入缓冲区
        V(mutex);            // ③ 解锁
        V(full);             // ④ 产品数 +1（可能唤醒消费者）
    }
}

consumer() {
    while (1) {
        P(full);             // ① 先申请产品——没有产品就阻塞
        P(mutex);            // ②
        take_item();         // 从缓冲区取出
        V(mutex);            // ③
        V(empty);            // ④ 空位 +1（可能唤醒生产者）
        consume_item();      // 消费（不需互斥）
    }
}
```

**为什么 `P(empty)` 必须在 `P(mutex)` 之前（必考）**：
设缓冲区已满（`empty=0`）。生产者若先 `P(mutex)` 拿到锁，再 `P(empty)` 就阻塞在锁内——**抱着锁睡觉**；此时消费者要取产品，必须先 `P(mutex)`，拿不到锁也阻塞。结果：生产者等空位（只有消费者能腾），消费者等锁（只有生产者能放），**互相等待 → 死锁**。
缓冲为空时消费者先 `P(mutex)` 再 `P(full)` 同理死锁。**口诀：先申请资源信号量，再加互斥锁。**

**为什么两个 V 可以交换**：`V` 不会阻塞，先 `V(mutex)` 还是先 `V(full)` 都不会造成循环等待，只影响被唤醒进程何时能真正进入临界区（晚醒一会儿而已），不影响正确性。

**注意边界**：`produce_item()` 和 `consume_item()` **不加锁**——生产、消费是各进程私有的操作，只有"放入/取出"缓冲区这一下才互斥。把整段生产也锁起来会严重降低并发。

#### 2. 多生产者-多消费者（奇偶分类，课后原题）

题：N 个单元的缓冲区；P1 用 `produce()` 生成正整数、用 `put()` 放入；P2 用 `get()` 取奇数并统计个数；P3 取偶数并统计。`put/get` 是访问缓冲区的操作。

**关键**：`full` 必须拆成 `odd` 和 `even` 两个信号量——只用一个 `full` 的话，"缓冲区里有东西"并不等于"有奇数"或"有偶数"，P2 可能取到偶数。

```c
semaphore mutex = 1;   // 缓冲区互斥
semaphore empty = N;   // 空位数
semaphore odd   = 0;   // 奇数个数
semaphore even  = 0;   // 偶数个数

P1() {
    while (1) {
        x = produce();
        P(empty);
        P(mutex);
        put(x);
        V(mutex);
        if (x % 2 == 1) V(odd);  else V(even);   // 按奇偶分别唤醒
    }
}

P2() {
    while (1) {
        P(odd);              // 先确认有奇数
        P(mutex);
        x = get();           // 取出一个奇数
        V(mutex);
        V(empty);            // 腾出一个空位
        count_odd(x);        // 统计，不需互斥
    }
}

P3() {
    while (1) {
        P(even);
        P(mutex);
        x = get();
        V(mutex);
        V(empty);
        count_even(x);
    }
}
```

`mutex` 在这里**同时管三对互斥**：放与取、取奇数与取偶数、放与放。若奇数消费者被阻塞，只有放入奇数才能唤醒它；偶数同理。

#### 3. 读者-写者（教材补充；408 十几年未考，老师留到强化）

规则：允许多个读者同时读；读者与写者互斥；写者与写者互斥。

```c
int count = 0;          // 当前正在读的读者数
semaphore rw    = 1;    // 读写互斥、写写互斥
semaphore mutex = 1;    // 保护 count 这个共享变量

writer() {
    while (1) {
        P(rw);          // 有读者或有写者则等
        writing();
        V(rw);
    }
}

reader() {
    while (1) {
        P(mutex);
        if (count == 0) P(rw);   // 第一个读者负责"锁住写者"
        count++;
        V(mutex);
        reading();               // 多个读者可同时读
        P(mutex);
        count--;
        if (count == 0) V(rw);   // 最后一个读者负责"放行写者"
        V(mutex);
    }
}
```

**顺序要点**：`if(count==0) P(rw)` 必须写在 `P(mutex)` 之内——`count` 的判断与自增必须原子。若把 `P(rw)` 提到 `P(mutex)` 之前，**每个读者都要抢 rw**，读者之间也变成互斥，违背"读者可同时读"的题意。

缺陷：读者源源不断时写者可能一直等 → **写者饥饿**。改进需再加一个"排队"信号量（教材补充：`semaphore w=1`，写者先 `P(w)`，读者也在 `P(mutex)` 前 `P(w); V(w)`），此处不展开。

#### 4. 哲学家进餐（教材补充；408 只考过 1 次）

问题：5 位哲学家围坐，5 只筷子，每人需同时拿起左右两只才能进餐。若 5 人同时各拿左边一只，则全部等右边 → 死锁（满足循环等待）。

**方案一：最多允许 4 人同时取筷（破坏循环等待）**

```c
semaphore chopstick[5] = {1,1,1,1,1};
semaphore count = 4;                  // 至多 4 人同时竞争

Pi() {                                 // i = 0..4
    while (1) {
        P(count);                      // ① 先限流
        P(chopstick[i]);               // ② 拿左筷
        P(chopstick[(i+1) % 5]);       // ③ 拿右筷
        eating();
        V(chopstick[i]);               // ④ 放左
        V(chopstick[(i+1) % 5]);       // ⑤ 放右
        V(count);                      // ⑥
    }
}
```

原理：4 人抢 5 只筷子，由抽屉原理必有 1 人能拿到两只，故不会出现全员各持一只的环。

**方案二：奇偶编号不同顺序（破坏循环等待）**

```c
Pi() {
    while (1) {
        if (i % 2 == 0) { P(chopstick[i]); P(chopstick[(i+1)%5]); }  // 偶数先左后右
        else            { P(chopstick[(i+1)%5]); P(chopstick[i]); }  // 奇数先右后左
        eating();
        V(chopstick[i]); V(chopstick[(i+1)%5]);
    }
}
```

相邻两人的取筷顺序相反，无法形成"每人持一只等另一只"的单向环。

**方案三：互斥地一次拿两只（破坏请求并保持）**

```c
semaphore mutex = 1;
Pi() {
    while (1) {
        P(mutex);                       // 拿筷子这一步整体互斥
        P(chopstick[i]);
        P(chopstick[(i+1)%5]);
        V(mutex);
        eating();
        V(chopstick[i]); V(chopstick[(i+1)%5]);
    }
}
```

不会死锁（要么两只都拿到，要么一只都没拿），但一次只允许一个人取筷，**并发度极低**。

#### 5. 管程（教材补充，概念级）

管程把"共享数据结构 + 对该结构的所有操作 + 同步机制"封装成一个模块，进程只能通过管程提供的入口过程访问共享数据，**管程内过程互斥执行由编译器保证**，程序员不必自己写 PV。管程内用**条件变量**（`x.wait()` 阻塞、`x.signal()` 唤醒）处理同步，与信号量的区别是：条件变量没有值、`signal` 时若无进程等待则**信号丢失**。Java 的 `synchronized` 方法即管程思想。

### 五、死锁（2.4，只考选择题）

#### 1. 定义与三个概念的区别

**定义**：多个进程因竞争资源而陷入僵局，**互相等待对方手里的资源**，若无外力干预都无法推进。

| 对比项 | 死锁 | 饥饿 | 死循环 |
|---|---|---|---|
| 进程数 | **至少 2 个**（互相等待成环） | 1 个进程也可发生 | 1 个即可 |
| 状态 | **必定是阻塞态** | 可能就绪态（长期上不了 CPU），也可能阻塞态（长期等 I/O） | 运行态（一直占 CPU） |
| 原因 | 竞争资源 + 推进顺序不当 | 调度策略不公平 / 资源长期被抢占 | 程序逻辑错误（循环条件永真） |
| 能否自行解除 | 不能，需外力 | 可能（竞争者退出后自动获得） | 不能（除非中断） |
| 解决 | 剥夺资源、撤销进程、回退 | 提高优先级、公平调度 | 改代码 / 终止进程 |

老师强调：**死锁与饥饿都是"无法向前推进"，但饥饿一个进程就能发生，死锁至少要两个；死锁一定阻塞，饥饿不一定。**

#### 2. 四个必要条件（必记）

| 条件 | 含义 | 反例（破坏后为何不死锁） |
|---|---|---|
| **互斥** | 资源必须互斥使用（一次只能一个进程用） | 资源若能共享，就无需竞争 |
| **不可剥夺** | 进程已获得的资源，未用完前不能被强行夺走 | 若能强行夺走，就不必互相等 |
| **请求并保持** | 进程已持有至少一个资源，又提出新请求且被阻塞，同时**不释放已有资源** | 若一次性拿全或先放再要，就不会"拿一半等一半" |
| **循环等待** | 存在进程—资源的**环形等待链**：P1 等 P2 的资源，P2 等 P1 的资源 | 若无环，总有一个进程能拿到全部资源先跑完 |

课上标准例子：P1、P2 都需要 A 和 B。A 分给 P1、B 分给 P2 → P1 持 A 求 B，P2 持 B 求 A → 互相僵持。此时四个条件全占：A、B 互斥；不可剥夺；各持一个再求一个；成环。

#### 3. 资源分配图与"有环 ≠ 死锁"

画法：**圆圈 = 进程，方框 = 资源**（方框内小圆点 = 该类资源的实例数）；**进程 → 资源 = 请求边**，**资源 → 进程 = 分配边**。

**关键结论**（选择题高频）：
- 资源分配图中**存在环，不一定死锁**；
- 若**每类资源只有一个实例**，则**有环 ⟺ 死锁**；
- 每类资源有多个实例时，有环只是"可能死锁"，还要看能否化简。

课上例子：P0 等 P1、P1 等 P2 …… PN 等 P0，看似成环。但若 PN 除了等 P0，还等着 Pk，而 Pk 并不在这条环上、能先执行完并释放资源，则 PN 拿到资源后可依次推进，**不死锁**。原因是该类资源有 2 个实例，一个分给 P0、一个分给 Pk，PN 等的不是"环上那个唯一实例"。

#### 4. 处理策略总览（三分法，字眼要抠死）

| 策略 | 思路 | 时机 | 典型方法 |
|---|---|---|---|
| **预防** | **破坏四个必要条件中的一条或多条** | 事前 | 破坏互斥/不可剥夺/请求并保持/循环等待 |
| **避免** | 分配前用算法判断分配后是否进入**不安全状态** | 事中（每次分配时） | **银行家算法** |
| **检测与解除** | 平时不管，发生死锁后检测并解除 | 事后 | 资源分配图化简；剥夺/撤销/回退 |

**408 对字眼极敏感**：看到"破坏四个必要条件"→ 只能答**预防**，答"避免"就错。

#### 5. 死锁预防（破坏哪一条 ↔ 用哪种方法）

| 破坏的条件 | 方法 | 具体做法 | 缺点 / 注意 |
|---|---|---|---|
| 互斥 | 资源共享（SPOOLing 假脱机） | 把独占设备改造成共享设备（打印机 → 共享打印队列） | **一般不可行**，资源固有属性决定，强行共享会出错 |
| 不可剥夺 | 剥夺式分配 | 进程请求新资源得不到满足时，**由系统强制其释放**已占资源（注意：是系统剥夺，不是别的进程直接抢） | 实现复杂、开销大；仅适用于 CPU、内存等可保存/恢复的资源 |
| 请求并保持 | **静态分配**（一次性分配） | 运行前一次性申请**全部**所需资源，拿不全就不运行 | 资源利用率低、可能饥饿（如 P1 需 4 个资源，等 4 个齐才给） |
| 请求并保持 | 先释放再申请 | 用过的资源先释放，再申请新资源 | 编程麻烦，释放后可能申请不回来 |
| 循环等待 | **资源有序分配** | 给每类资源编号，进程**只能按编号递增**的顺序申请 | 编号固定、限制编程；新增资源类别时难以插入 |

**资源编号例子（课上）**：资源 S1、S2、S3；P1 需 S2、S3；P2 需 S1、S3；P3 需 S1、S2。不规定顺序时：P1 拿 S2、P3 拿 S1、P2 拿 S3，三方各持一个再求下一个 → 死锁。

规定**按编号递增申请**后，P2 只能先 S1 后 S3，P1 先 S2 后 S3，P3 先 S1 后 S2：
- P2 先拿 S1，则 P3 拿不到 S1，而 P3 **不许跳过小编号去拿 S2**，于是 P3 一个都不占；
- P2 再申请 S3 成功，两资源齐全 → 执行完释放；
- 释放后 P1 能拿 S3、P3 能拿 S1，逐个推进，**不会死锁**。

本质：编号递增使得"持大号等小号"不可能发生，**环无法形成**。

#### 6. 死锁避免：安全状态与安全序列

- **安全状态**：系统能找到一个进程执行序列，使每个进程都能获得所需资源并完成。
- **安全序列**：这样的进程推进顺序（**不唯一**）。
- **不安全状态**：找不到任何安全序列。**不安全 ≠ 死锁**，只是"可能死锁"。

**结论（背）**：
- 处于安全状态 → **一定不会**死锁；
- 处于不安全状态 → **可能**死锁，不是必然；
- 死锁状态 → 一定是不安全状态。

**入门算例（12 台打印机）**：P1 最多需 10 台，已分 5；P2 最多需 4 台，已分 2；P3 最多需 9 台，已分 2；当前可用 = 12 − 9 = 3 台。

| 进程 | 最大需求 | 已分配 | 尚需 |
|---|---|---|---|
| P1 | 10 | 5 | 5 |
| P2 | 4 | 2 | 2 |
| P3 | 9 | 2 | 7 |
| 合计 | — | 9 | — |

推进过程：

| 步 | 可用 | 选中 | 尚需 ≤ 可用？ | 完成后可用 = 可用 + 已分配 |
|---|---|---|---|---|
| 1 | 3 | P2 | 2 ≤ 3 ✓ | 3 + 2 = 5（P2 释放全部 4 台，其中 2 台本就占着） |
| 2 | 5 | P1 | 5 ≤ 5 ✓ | 5 + 5 = 10 |
| 3 | 10 | P3 | 7 ≤ 10 ✓ | 10 + 2 = 12 |

安全序列：**P2 → P1 → P3**。注意第 1 步若把 3 台分给 P1（需 5）或 P3（需 7）都不够，会导致谁都跑不完。

#### 7. 银行家算法完整算例（课后 36，真题原题）

**四个量**：
- 资源总量 `Resource`：系统各类资源的总数；
- 最大需求 `Max`：每个进程最多要多少；
- 已分配 `Allocation`：当前已给它多少；
- 尚需 `Need = Max − Allocation`；
- 可用 `Available = Resource − ΣAllocation`。

**T0 时刻数据**（Available = (2,3,3)，资源总量 (18,6,22)）：

| 进程 | Max (A,B,C) | Allocation | Need | 备注 |
|---|---|---|---|---|
| P0 | (5,5,10) | (3,2,3) | **(2,3,7)** | |
| P1 | (5,3,6) | (4,0,3) | **(1,3,3)** | |
| P2 | (4,0,11) | (4,0,5) | **(0,0,6)** | |
| P3 | (4,2,5) | (2,0,4) | **(2,2,1)** | |
| P4 | (4,2,4) | (3,1,4) | **(1,1,0)** | |
| 合计 | — | (16,3,19) | — | 18−16=2，6−3=3，22−19=3 |

验算：`ΣAllocation = (3+4+4+2+3, 2+0+0+0+1, 3+3+5+4+4) = (16,3,19)` → `Available = (18,6,22) − (16,3,19) = (2,3,3)` ✓

**安全性检查（逐步表）**：

| 步骤 | Work (A,B,C) | 试探进程 | Need ≤ Work？ | 完成后 Work = Work + Allocation |
|---|---|---|---|---|
| 0 | (2,3,3) | — | — | — |
| 1 | (2,3,3) | **P3** | (2,2,1) ≤ ✓ | (4,3,7) |
| 2 | (4,3,7) | **P4** | (1,1,0) ≤ ✓ | (7,4,11) |
| 3 | (7,4,11) | **P2** | (0,0,6) ≤ ✓ | (11,4,16) |
| 4 | (11,4,16) | **P1** | (1,3,3) ≤ ✓ | (15,4,19) |
| 5 | (15,4,19) | **P0** | (2,3,7) ≤ ✓ | **(18,6,22)** |

**安全序列：P3 → P4 → P2 → P1 → P0**（对应正确选项）。

排除过程（怎么快速选出答案）：
- 第一步 `Available=(2,3,3)`：
  - P0 需 (2,3,7)：R3 要 7 > 3 ✗ → **一切以 P0 开头的选项全排除**；
  - P2 需 (0,0,6)：R3 要 6 > 3 ✗ → **一切以 P2 开头的选项全排除**；
  - P1 需 (1,3,3) 可行，P3、P4 也可行。
- 若按 P1 开头：完成后 Work = (2,3,3)+(4,0,3) = (6,3,6)，此时 P0 还缺 7 个 R3（> 6）✗，**P1 后紧跟 P0 的选项排除**（老师就是用它排掉干扰项）。
- 顺推完 P3 开头的序列，Work 最终回到 (18,6,22)。

**校验技巧**：所有进程执行完后，`Work` 必须**恰好等于资源总量**。算不出 (18,6,22) 说明前面某步加错了。

#### 8. 死锁检测与解除

**检测：化简资源分配图**

步骤：
1. 算出每类资源的**空闲数 = 总数 − 已分配数**（方框内点数 − 出去的分配边数）；
2. 找一个**请求边能被满足**（所需 ≤ 空闲数）的进程；
3. 假定它运行完毕，**删除它的所有边**（请求边 + 分配边），使其成为孤立结点，资源全部归还；
4. 重复 2、3，若最终**能删除所有边**，称图**可完全简化**，**无死锁**；若还剩边相连的进程，这些进程就是**死锁进程**（死锁定理）。

课上例：R1 共 3 个实例、全部分出；R2 共 2 个、分出 1 个（空闲 1）。P1 请求 R2、P2 请求 R1。
- 第 1 轮：R2 空闲 1，满足 P1 → 删 P1 所有边，R1 空闲变为 3−1=2、R2 空闲 1；
- 第 2 轮：R1 空闲 2，满足 P2（只需 1）→ 删 P2 所有边；
- 边全删完 → **可完全简化 → 系统无死锁**（只是暂时都在等，但能解开）。

**解除三法**：

| 方法 | 做法 | 代价 |
|---|---|---|
| 资源剥夺法 | 从死锁进程处**强行抢占**资源，分配给其他进程，打破环路 | 被剥夺者可能仍无法推进；需防止反复被剥夺导致饥饿 |
| 撤销进程法 | 直接**终止**部分（或全部）死锁进程，回收其资源 | 进程此前工作**全部丢失**，重跑要从头来 |
| 进程回退法 | 让进程**回退到**死锁发生前的某个检查点，再重新推进 | 需系统保存历史信息（检查点），开销大；回退后因异步性可能不再死锁 |

## 老师强调的考点

1. **PV 操作大题必考**（2.3 课后 13 道大题里八九道是同一类型），生产者-消费者模板**必须默写**，选择题 47–56 共 10 道也全出自本节。
2. **信号量的个数、含义、初值、PV 位置**是核心采分点：多定义一个（想复杂了）或少定义一个（漏分析关系）都扣分，一个大题 7 分，可能扣 1–2 分。
3. **同步与互斥的判定**：同步 = 有先后顺序；互斥 = 不许同时。**互斥信号量初值 1，同步信号量初值 0**。
4. **P(empty)/P(full) 必须写在 P(mutex) 之前**，写反一定死锁，属"逻辑错误扣分较多"。
5. **四个必要条件必记**（选择），且能对着例子指出四条各体现在哪。
6. **预防 vs 避免的字眼抠得极死**：破坏四个必要条件 = 预防；银行家算法 = 避免。
7. **银行家算法是常规计算题，真题考过多次**，必须会画安全性检查表、会写安全序列。
8. **资源分配图有环不一定死锁**；每类资源只有一个实例时，有环必死锁。
9. **死锁 vs 饥饿**（选择）：死锁至少两个进程且必定阻塞；饥饿一个进程即可，可能处于就绪态。
10. **不同临界区要配独立的互斥信号量**（打印机 1、打印机 2 不能共用一个 mutex）。
11. 题干若写 `wait/signal`，答案就写 `wait/signal`；写 `PV` 也行，但**审题跟随题干**。
12. 前驱图：**每条边一个信号量，初值 0**；**同一线程内部的顺序不用设信号量**（26 题设 5 个就错）。

## 快速技巧与口诀

**1. 信号量定值口诀**
> **资源数 = 信号量初值**；临界区就是 1 个资源，所以 mutex 恒为 1；同步的"资源"还没产生，所以初值 0；系统本来就有存货（信箱已有 X 封），初值就写 X。

**2. 同步写法口诀**
> **前 V 后 P**：先发生的动作后面 V，后发生的动作前面 P，初值 0。想让谁后执行，就在谁前面塞一个 P。

**3. 互斥写法口诀**
> **PV 夹临界区，一锁一开成对出现**；P = 加锁，V = 解锁；锁住的只能是访问临界资源那几行。

**4. 前驱图口诀**
> **一条边一个信号量，初值全 0**；边的起点动作后 V，终点动作前 P；入度是几，前面就写几个 P。

**5. 生产者消费者 PV 顺序口诀**
> **先资源、后互斥**（empty/full 在前，mutex 在后）；**V 的顺序无所谓**，P 的顺序要命。

**6. 银行家算法三步**
> `Need = Max − Allocation`；`Available = 总量 − ΣAllocation`；拿 `Need` 与 `Work` 逐项比，**全都 ≤ 才可推进**，推进后 `Work += Allocation`。

**7. 银行家校验口诀**
> 全部进程跑完，`Work` 必然回到**资源总量**；不相等 = 算错。

**8. 死锁最小进程数公式**（同类资源，每个进程最多需 m 个，共 R 个）
> 每个进程先给 `m−1` 个，若还能分完则可能死锁：`K(m−1) ≤ R` 时可死锁。
> **K_min = ⌊(R−1)/(m−1)⌋ + 1**。
> 例：R = 8，m = 3 → ⌊7/2⌋+1 = **4**（4 个进程各拿 2 台，8 台刚好分完，人人缺 1 台）；3 个进程时每人 2 台只用 6 台，剩 2 台必能凑齐一人 → 不死锁。

**9. 信号量值速读**
> 值为正 → 剩几个资源；值为负 → 几个进程在等；值 = 初始值 − 已被拿走数。

## 易错点与坑

1. **生产者消费者两个 P 写反**：先 `P(mutex)` 后 `P(empty)`，缓冲区满时生产者抱锁等空位、消费者等锁 → 死锁。这是本节最容易失分的一处。
2. **同步信号量初值写成 1**：初值为 1 时 `P` 不阻塞，"后发生的进程"照样能先跑，同步失效。**同步初值必须是 0**（除非系统初始已有该资源）。
3. **信箱/仓库题初值照抄容量**：课后 21 题 A 信箱容量 M、已有 X 封，则 `empty_A = M − X`、`full_A = X`（不是 0）。照抄 M、N 直接错。
4. **信号量为负的含义搞反**：`S = −2` 表示**有 2 个进程在等待**（还缺 2 个资源），不是"还剩 2 个资源可用"。
5. **多定义信号量**：26 题两线程里，A→E、E→F、B→C、C→D 是**同一线程内部**的顺序，代码天然保证，设 5 个信号量必扣分，正确只设 2 个。
6. **多个临界区共用一个 mutex**：两组进程用不同打印机却共用一个信号量，造成过度互斥（本是并发变成串行）。
7. **把 `produce_item()` / `consume_item()` 也放进临界区**：不影响互斥正确性，但严重降低并发，且与题意不符（题目通常明说只有 put/get 互斥）。
8. **"资源分配图有环 = 死锁"**：错。只有**每类资源单实例**时才等价；多实例有环可能只是"暂时都在等"，化简后可能无死锁。
9. **把"破坏互斥"当可行方案**：破坏互斥在实践中基本不可行（资源属性决定），只能靠 SPOOLing 这类技术改造少数设备。
10. **银行家算法算错 Work**：进程完成后要把**它已分配的全部资源**加回 Work（不是只加 Need），且 Work 单调不减；最后必须等于资源总量。
11. **混淆"不安全状态"和"死锁"**：不安全只是"可能死锁"；安全状态才保证"一定不死锁"。
12. **死锁与饥饿混答**：死锁进程**必处于阻塞态**；饥饿进程可能在**就绪态**（长期没被调度）。另外"死锁至少两个进程"也是常考点。
13. **记录型信号量 P 里判 `<0`、V 里判 `<=0`**，符号写错全盘皆错；整型信号量则是 `while(S<=0); S--`，先判后减，顺序也不同。
14. **前驱图漏 P**：一个动作有两条入边，前面必须写两个 P，漏一个就变成"任一前驱完成即可"，语义错。

## 本章例题

**例 1（课后 47，信号量数值）**
某资源信号量初值为 3，当前值为 1，问：该资源可用个数、等待该资源的进程数各是多少？
解：
1. 当前值 1 > 0，表示还有 **1 个**资源可用；
2. 值为正说明无进程阻塞，等待进程数 = **0**；
3. 初值 3 减当前值 1 = 2，说明已有 **2 个**进程各拿走 1 个资源。
答：可用 1 个，等待 0 个，已被占用 2 个。
变式：若当前值为 −1，则可用的为 0（还缺 1 个），**有 1 个进程在等待**。

**例 2（课后 26，两个线程的前驱，易错题）**
某进程的两个线程 T1、T2 并发执行：T1 依次执行 A、E、F，T2 依次执行 B、C、D。要求 A 在 C 之前、C 在 E 之前。用 wait/signal 描述同步关系。

解：
1. **辨认同线程内部顺序**：A→E→F、B→C→D 由线程自身顺序保证，**不设信号量**；
2. 跨线程的约束只有两条边：A→C、C→E，故**只需 2 个信号量**，初值均 0；
3. 每条边：起点后 `signal`，终点前 `wait`。

```c
semaphore SAC = 0;      // 保证 A 在 C 之前
semaphore SCE = 0;      // 保证 C 在 E 之前

T1() {
    A;
    signal(SAC);        // A 完成，放行 C
    wait(SCE);          // 等 C 完成
    E;
    F;
}

T2() {
    B;
    wait(SAC);          // 等 A 完成
    C;
    signal(SCE);        // C 完成，放行 E
    D;
}
```
答：定义 2 个初值为 0 的信号量即可（题干要求 `wait/signal`，就不要写成 P/V）。

**例 4（课后 21，双信箱 = 两组生产者消费者）**
A、B 两人通过信箱辩论：向 A 信箱放信 = A 的生产者，从 A 信箱取信 = A 的消费者；B 同理。A 信箱最多 M 封且已有 X 封，B 信箱最多 N 封且已有 Y 封。

解：
1. 两组独立的"生产者-消费者"，各配一套信号量（不同临界区 → 独立信号量）；
2. 初值按"已有存货"定：`empty_A = M−X`，`full_A = X`；`empty_B = N−Y`，`full_B = Y`；
3. 互斥信号量 `mutexA = mutexB = 1`；
4. 每组内部仍是"先资源、后互斥"。

```c
semaphore mutexA = 1, emptyA = M-X, fullA = X;
semaphore mutexB = 1, emptyB = N-Y, fullB = Y;
```
题干只说"同步关系"也可能暗含互斥（信箱本身是临界资源），**以自己分析为准**。

**例 7（课后 34，死锁最小进程数）**
系统有 8 台打印机，K 个进程，每个进程最多需要 3 台。问 K 至少为多少时才**可能**发生死锁？

解：
1. 让每个进程都"差一台"，即各持有 `3−1 = 2` 台；
2. 8 台刚好够 4 个进程各拿 2 台，此时人人缺 1 台，谁也拿不到第 3 台，8 台全部分完 → **死锁**；
3. 若只有 3 个进程：各拿 2 台只用 6 台，还剩 2 台，必有一个进程能凑齐 3 台 → 一定不死锁。
答：**K 最小为 4**。
（注意题目问"可能死锁的最小值"，5 个、8 个进程也可能死锁，但最小值是 4。）

**例 8（资源分配图化简）**
R1 有 3 个实例全部分出，R2 有 2 个实例分出 1 个；P1 请求 R2，P2 请求 R1。判断是否死锁。
解：R2 空闲 1 → 满足 P1 → 删 P1 全部边，R1 空闲变为 2 → 满足 P2 → 删 P2 全部边 → **图可完全简化 → 无死锁**。
